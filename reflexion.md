## **1\. ¿Cuántos tests unitarios, de integración y E2E tenés? ¿Por qué esa proporción?**

En mi TP preparé tests unitarios para comprobar las reglas de negocio de checkout.py, tests de integración para verificar la persistencia en SQLite y tests E2E para probar la API mediante requests HTTP reales. En integración escribí casos para comprobar que los pedidos y sus ítems se guarden correctamente, que los importes mantengan su precisión y que los datos se normalicen. En E2E agregué pruebas para la creación y consulta de pedidos, además de los errores HTTP definidos en la especificación. La cantidad exacta de tests de cada categoría todavía tengo que confirmarla, porque al ejecutar pytest \--collect-only \-q obtuve el resultado collected 0 items. Los tests unitarios deberían ser los más numerosos porque permiten comprobar muchas combinaciones de datos de manera rápida y aislada. Los tests de integración y E2E complementan esa suite porque detectan problemas que aparecen cuando interactúan la base de datos, la API y las reglas de negocio.

## **2\. ¿Qué falla de pedidos.py no podía encontrarse con un test unitario de checkout.py? ¿Por qué?**

Una falla que no puede detectarse únicamente con tests unitarios de checkout.py es que pedidos.py guarde o recupere incorrectamente los importes de una compra. Por ejemplo, la especificación establece que el descuento de una remera de \$11.999,50 con el cupón EGRESADOS2026 debe ser exactamente Decimal("1799.93"). Aunque checkout.py calcule correctamente ese descuento, la capa de persistencia podría alterar su precisión al guardarlo en SQLite o al recuperarlo. Para comprobarlo escribí un test de integración que guarda un pedido y compara los importes recuperados con los valores esperados. También preparé una prueba para verificar que una compra inválida no deje registros en las tablas pedidos e items. Estos comportamientos dependen de la interacción con la base de datos y no se pueden verificar completamente probando solo las funciones de cálculo. Para determinar cuál de estas fallas existe realmente en el código original, tendría que ejecutar los tests y analizar sus resultados.

## **3\. ¿Qué falla de api.py estaba en el paso de información entre dos partes del sistema? ¿Qué parte tendría que haberla resuelto?**

Una posible falla en el intercambio de información entre la API y la capa de persistencia ocurre cuando api.py recibe datos HTTP y no los valida o transforma correctamente antes de procesarlos. Un ejemplo concreto es el campo fecha, que el cliente envía como texto con formato AAAA-MM-DD. Si se recibe el valor "30-11-2026", la API debe responder con estado HTTP 400 y el código FECHA\_INVALIDA, en lugar de provocar un error interno 500\. Para comprobar ese comportamiento preparé un test E2E que envía una fecha con formato incorrecto y verifica la respuesta. La responsabilidad de validar el formato de la fecha recibida corresponde a api.py, mientras que la validación de las reglas del cupón corresponde a checkout.py. Una prueba HTTP permite comprobar que el error se traduzca correctamente y llegue al cliente con el estado y el código establecidos. Como todavía no pude confirmar el resultado de esa prueba, debo distinguir este caso esperado de una falla efectivamente demostrada.

## **4\. ¿Cuál de las fallas que encontraste habría sido la más cara de descubrir en producción? ¿Por qué?**

Una de las fallas potencialmente más costosas sería que un pedido se guardara parcialmente en la base de datos, por ejemplo, con el registro principal en pedidos pero sin todos sus ítems en items. Esto podría provocar que la tienda confirmara una compra que después no pudiera reconstruir correctamente. También podría generar reclamos de los compradores y dificultar el trabajo administrativo de la comisión de egresados. Para detectar ese riesgo preparé un test de integración que guarda un pedido y lo consulta desde una segunda conexión a SQLite. Además, la especificación establece que, si el checkout devuelve un error, no debe quedar guardado ni el pedido ni ninguno de sus ítems. Considero que esta falla sería grave porque afecta la integridad de los datos y podría pasar inadvertida si solo se comprueba que la API devuelve una respuesta exitosa. Sin embargo, para afirmar que fue la falla más grave encontrada en mi TP, primero tendría que confirmar los resultados de las pruebas contra el código original.

## **5\. ¿Qué mide la cobertura, qué mide la mutación y qué mide la inyección de fallas? ¿En qué se diferencian?**

La cobertura mide qué partes del código se ejecutan durante las pruebas y, con la opción de ramas, permite comprobar qué caminos de decisión fueron recorridos. Sin embargo, una cobertura alta no garantiza que los tests verifiquen correctamente los resultados. La mutación evalúa si los tests detectan cambios artificiales en el código, como modificar un límite de cantidad o alterar una condición de descuento. Si una mutación relevante no hace fallar ningún test, puede significar que falta una aserción que compruebe ese comportamiento. La inyección de fallas consiste en introducir deliberadamente errores o condiciones problemáticas para comprobar si las pruebas permiten detectarlos. En este TP, mutar.py se utiliza para medir la capacidad de detección de mutaciones, mientras que los tests de integración y E2E comprueban cómo responde el sistema ante entradas inválidas y errores entre capas. En conclusión, la cobertura mide ejecución, la mutación mide la sensibilidad de los tests ante cambios y la inyección de fallas permite evaluar la detección de problemas provocados.

## **6\. Si una IA escribiera tus tests de integración y E2E, ¿qué le faltaría probar? ¿Cómo lo comprobarías?**

Si una IA escribiera mis tests de integración y E2E, revisaría que cubrieran todos los requisitos de R10 y R11, en lugar de limitarse a comprobar los casos exitosos. Por ejemplo, comprobaría que una compra inválida no deje pedidos ni ítems guardados en SQLite y que otra conexión pueda recuperar un pedido completo después de guardarlo. En la API verificaría que cada error tenga el estado HTTP y el código establecidos por la especificación, y que ninguna entrada inválida provoque una respuesta 500\. También comprobaría que los importes viajen como cadenas JSON y no como números, porque la especificación exige preservar su representación decimal. Para encontrar casos omitidos, compararía cada regla con los tests existentes y agregaría pruebas para límites, tipos incorrectos, fechas inválidas y rutas inexistentes. Después ejecutaría la suite contra el backend original y revisaría si los fallos detectados corresponden realmente a incumplimientos del contrato. Finalmente, utilizaría cobertura, mutación y revisión manual para identificar caminos no probados y comprobar que las aserciones detecten errores importantes.
